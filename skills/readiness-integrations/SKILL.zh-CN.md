# 集成审查

审查真实外部依赖和面向客户的集成接口。产品没有公共 API、沙箱或开发者平台需求时，不能强行要求这些功能。

## 适用性

产品存在出站/入站 API、Webhook、OAuth、合作方服务、客户 API 密钥、集成凭据或事务邮件时使用。支付专用资金后果归 R-04，队列基础设施归 R-07；本技能主责集成真实性、接口契约和投递行为。

## 需要检查的证据

检查 HTTP 客户端、超时、序列化、schema、回调、签名中间件、API 路由、密钥存储、OAuth 令牌存储、刷新任务、重试逻辑、投递日志、供应商配置、沙箱支持和邮件发送/抑制路径。DNS、供应商控制台、抑制名单和外部投递记录需要外部证据。

## 检查项

### 第三方 API 与 OAuth

- 请求需要适当超时、带退避/抖动的有界重试、取消和幂等意识，避免一次不稳定调用变成丢失或重复操作。
- 响应解析必须有意识地处理可选字段、错误、分页和 schema 演变。契约/集成测试及供应商变化监控应匹配依赖的重要程度。
- OAuth 令牌需要安全存储、过期处理、失败前刷新、并发控制、撤销处理和重新授权路径。
- 只有客户或合作方需要测试集成时才要求沙箱或测试环境；验证其行为真实性和与生产的隔离。

### Webhook 与客户 API

- 入站 Webhook 必须对正确负载验证真实签名，并具有时间戳/重放防护及支持时的密钥轮换。
- 回调处理必须安全处理重复、顺序、超时和重试。提供出站 Webhook 时，需要有界重试和失败投递/死信的持久记录。
- 公共 API 需要明确版本和兼容性策略，避免变化悄悄破坏现有集成。
- 客户 API 密钥必须可创建、可撤销、有范围、安全存储、按需展示，并纳入审计日志且不暴露密钥内容。
- API 限流必须保护共享资源，同时考虑突发、重试和真实集成负载；响应应帮助客户端恢复。

### 事务邮件

- SPF、DKIM 和 DMARC 必须针对实际发送域名和供应商检查。代码库或环境变量不能证明 DNS 配置正确。
- 退信和投诉事件必须按要求更新抑制/投递行为，尤其是密码重置和账单通知。
- 检查发件人/域名所有权、不同消息类型的退订或偏好义务、投递监控，以及持续供应商故障的可行动处理。

## 验证边界

未经授权，不得触发真实供应商回调、邮件、OAuth 授权或外部负载。使用已记录样本和授权测试/沙箱环境。未检查外部 DNS、供应商配置和真实投递行为时，标为无法确认。

## 输出

返回包含 `finding_id`、`R-06`、严重程度、状态、置信度、结论、具体丢失/重复/不安全集成场景、证据 ID/位置、验证、建议和缺失证据的发现。供应商侧未知项单独列出，两个语言版本的 ID 保持一致。要求文档输出时，成对保存 `readiness-integrations-report.en.md` 和 `readiness-integrations-report.zh-CN.md`，不覆盖已有报告。不修改集成配置，不发送真实事件。
