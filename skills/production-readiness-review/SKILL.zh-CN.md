# 生产就绪审查总控

你的职责是协调，不是代替所有专项。选择并汇总专项审查，不能编造证据，也不能机械执行整张清单。

## 不可违反的规则

- 被审查产品保持只读。不修改代码、配置、基础设施、依赖或外部服务。
- 未经明确授权，不运行破坏性测试、凭据攻击、生产负载测试或对外扫描。
- 只询问会实质影响审查范围的问题。其他情况先检查现有证据，并记录限制。
- 绝不能把“没有找到”写成“没有实现”“不适用”或“安全”。
- 绝不编造问题、已有控制、测试结果、文件、行号、认证或运营实践。
- 不把密钥、个人数据、银行卡数据、令牌或其他敏感值复制进报告。
- 中英文输出的范围、ID、发现、严重程度、证据、排序和限制必须一致。

## 必读参考文件

路由前阅读：

1. `references/project-profile.en.md` 或 `references/project-profile.zh-CN.md`，用于项目画像和路由矩阵。
2. `references/evidence-and-severity.en.md` 或 `references/evidence-and-severity.zh-CN.md`，用于状态、证据和排序。
3. 输出最终报告时，阅读 `references/report-template.en.md` 和 `references/report-template.zh-CN.md`。

上下文有限时，工作说明可只读一种语言，但必须保留两种输出版本。

## 专项目录

每个模块都必须出现在路由矩阵中，包括跳过的模块。

| 路由 ID | 技能名称 | 主责范围 |
|---|---|---|
| R-01 | `readiness-identity-access` | 身份认证、恢复、会话、授权、租户、企业身份 |
| R-02 | `readiness-application-security` | 密钥、依赖、输入、OWASP、上传、浏览器/安全边界、加密、权限、日志安全 |
| R-03 | `readiness-data-reliability` | 数据模型、迁移、查询、备份、恢复、时间/Unicode、通用幂等、导入导出、保留 |
| R-04 | `readiness-payments-billing` | 金额、扣款、订阅、发票、退款、税、计量、对账 |
| R-05 | `readiness-ai-safety` | 模型、提示词、Agent、提示数据、评测、模型费用、降级、人工批准 |
| R-06 | `readiness-integrations` | 外部 API、OAuth、Webhook、API 版本、客户密钥、沙箱、事务邮件 |
| R-07 | `readiness-operations` | 环境、交付、发布、队列、容量、灾备、遥测、事故、成本与存储运营 |
| R-08 | `readiness-quality-maintainability` | 测试、评审、依赖、代码健康、文档、支持工具、所有权、可维护性 |

## 工作流程

### 1. 建立项目画像

检查确定范围所需的实际源码、依赖清单、配置、测试、部署文件和文档。识别产品类型、运行入口、用户、租户、数据类别、资金流、AI 使用、外部集成、交付方式和已知运营边界。

不要为了让审查显得全面而读取无关文件。记录已检查根目录，以及私有后端、云账号、CI 系统、合同或生产遥测等不可用部分。

### 2. 路由所有模块

每个模块只能有一个路由决定：

- `RUN`：正向证据表明能力或风险存在，或者用户明确要求审查该模块。
- `NOT_APPLICABLE`：明确的产品范围证据和适当的技术检查共同支持排除，两者都要记录。
- `UNCONFIRMED`：证据不足，无法决定。尽可能执行有限范围的证据缺口检查，否则说明缺少什么。

仅凭缺少 SDK、关键词、界面或仓库文件，不能证明能力不存在。一个模块可以是 `RUN`，其中个别检查项仍是 `NOT_APPLICABLE` 或 `UNCONFIRMED`。

### 3. 执行所选专项

使用 Skill 工具，按目录中的准确名称调用所选专项。传递项目画像、已检查范围、用户限制、路由 ID 和已知证据缺口。对于 `UNCONFIRMED` 路由，要求专项分析证据缺口，不能假设完整能力已经存在。

如果所需专项不可用或无法完成，将其执行状态标为 `NOT_REVIEWED` 并解释原因，不能模拟其结果。

专项可能发现挑战初始路由的证据。应明确重新评估路由，并保留最终决定的理由。

### 4. 汇总并排序

使用共享证据指南规范化专项结果。合并不丢失证据的重复发现。优先处理已确认的数据泄露、资金损失、不可恢复数据丢失和服务中断，再考虑可利用性、影响范围、可能性和证据置信度。

最多报告 10 个重点问题；已验证问题不足时，列表就应更短。低优先级结果和证据缺口放在各自章节，不能为了提高优先级而夸大严重程度。

### 5. 生成双语版本

两个版本使用稳定且相同的路由 ID（`R-01`…`R-10`）、发现 ID（如 `F-APPSEC-001`）和证据 ID（`E-001`…）。只翻译自然语言，不翻译路径、代码、配置键、命令和标识符。

用户要求文档输出时，在用户指定或新建的报告目录中同时创建 `readiness-report.zh-CN.md` 和 `readiness-report.en.md`。先检查目标，不覆盖已有报告。报告文件是唯一允许写入的内容，产品文件保持不动。

用户只要求聊天输出时，提供内容等价的中英文版本，不能声称已经保存文件。

## 最终质量门禁

交付前确认：

- 每条路由都有决定、理由、证据和缺口。
- 每个确认问题和确认已有控制都有可复核证据。
- `UNCONFIRMED` 和 `NOT_REVIEWED` 清晰可见，且没有被计为通过或漏洞。
- 两个版本的 ID、数量、严重程度、排序和限制一致。
- 报告说明哪些内容没有经过动态测试。
- 没有修改产品代码或配置。
