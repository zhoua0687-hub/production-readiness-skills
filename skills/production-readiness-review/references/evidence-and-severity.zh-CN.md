# 证据、状态与严重程度

## 证据规则

1. 结论必须锚定可复核证据：`path:line`、配置键、schema 或迁移、测试名称和结果、命令结果，或可识别的外部记录。
2. 分配证据 ID（`E-001`、`E-002`…），并在两个语言版本中复用。密钥和敏感值必须脱敏。
3. 区分直接观察和推断。推断必须解释，不能写成已验证事实。
4. 仓库通常能支持代码级结论，但不能证明备份恢复、渗透测试、值班响应、权限复核、认证、合同或账号所有权。
5. 缺少文档不能证明运营实践不存在；只有政策文档也不能证明实践有效运行。
6. 记录搜索范围和不可用内容，不能声称执行过未运行的动态验证。

## 检查状态

| 状态 | 含义 |
|---|---|
| `CONFIRMED_ISSUE` | 证据支持一个具体缺陷或缺失的必要控制。 |
| `CONFIRMED_CONTROL` | 证据支持相关控制存在，但不保证不存在其他绕过方式。 |
| `NOT_APPLICABLE` | 根据已建立的产品或合同范围，该项不适用，并说明理由。 |
| `UNCONFIRMED` | 证据不足，无法决定；指出具体缺失证据。 |
| `NOT_REVIEWED` | 该项或模块未检查；解释执行限制。 |

不能把 `UNCONFIRMED` 或 `NOT_REVIEWED` 计为通过，也不能自动计为漏洞。

## 严重程度模型

严重程度反映实际产品环境中的影响，不是清单条目的重要程度。

| 严重程度 | 使用条件 |
|---|---|
| Critical | 存在可信的即时路径，可造成大范围数据泄露、重大资金损失、不可恢复数据丢失或核心服务长期中断，需要紧急处理。 |
| High | 现实场景可能造成实质数据暴露、未授权操作、资金错误、重大服务中断或恢复失败。 |
| Medium | 有意义的安全、可靠性、合规或资金弱点，需要前置条件或影响范围有限。 |
| Low | 运营、体验或可维护性影响有限，未发现可信的严重场景。 |
| Info | 背景说明或改进建议，不是缺陷，不计入重点问题数量。 |

置信度单独使用 `High`、`Medium` 或 `Low`。未知仍是未知，置信度标签不能把未知变成确认问题。

## 发现记录

每个确认问题使用以下字段：

```text
finding_id
module / route_id
severity
status
confidence
claim
risk_scenario
evidence_ids and locations
validation_performed
recommendation
missing_evidence
```

风险场景必须把行为者或事件与具体产品影响连接起来。建议应针对已证明的原因，不能凭空增加无关功能。

## 优先级排序

先按严重程度排列确认问题，再考虑现实可能性、影响范围、可逆性和证据置信度。最多展示 10 个重点问题，空位不能用通用建议填满。

确认已有控制、较低优先级观察、未知项、跳过模块和执行限制分别放在独立报告章节。

## 双语一致性

两个报告必须具有相同的路由 ID、发现 ID、证据 ID、数量、严重程度、置信度、排序、位置和限制。只翻译说明文字。交付前，如果一版发生变化，必须同步另一版。
