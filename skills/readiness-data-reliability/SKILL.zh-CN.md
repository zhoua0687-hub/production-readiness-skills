# 数据可靠性审查

审查深度必须匹配实际数据存储和产品承诺。本地内存工具不需要数据库迁移或每晚托管备份，但排除前必须明确它的持久化和恢复预期。

## 适用性

产品存在数据库、文件、本地持久化、共享状态、导入导出、后台写入、合同保留或恢复要求时使用。金额专用表示归 R-04；通用非支付幂等仍归本模块，即使支付不适用也不能遗漏。

## 需要检查的证据

检查 schema、模型、迁移、查询路径、索引、数据存储配置、连接生命周期、事务边界、任务、序列化、导入导出代码、删除路径，以及可用的备份/恢复/保留记录。云端备份、PITR、恢复演练和生产查询计划需要外部或运行时证据。

## 检查项

### 模型、迁移与规模

- 评估 schema 是否清晰表达真实实体、归属、不变量、唯一性、生命周期和扩展点。不能只凭风格就称 schema 是“AI 随手设计”。
- 迁移必须明确前向行为，并诚实说明回滚行为。不可逆变更要说明原因及数据保护方式，不能编造会丢数据的 down migration。
- 根据真实表规模检查锁定时长、表重写、回填、并发/索引策略和部署兼容性。未经批准，不得在实时数据上运行迁移。
- 根据实际过滤、连接、排序和基数检查索引与查询计划。深分页在新增/删除时必须保持稳定，并在规模需要时避免病态 offset。
- 连接获取、连接池、超时、事务范围和并发不能在合理流量突发下耗尽数据存储。

### 恢复与删除

- 每晚或其他适当频率的备份必须匹配恢复目标。备份配置与真实恢复演练证据分别确认。
- 只有恢复目标需要时才要求 PITR；验证覆盖范围、保留期和恢复过程，不能假设供应商功能已经开启。
- 产品承诺误删恢复时，软删除或撤销应提供支持，同时遵守保留和删除义务。不能要求所有记录一律软删除。

### 正确性与数据交换

- 时间点必须无歧义存储，通常使用 UTC，并为未来/本地提醒保留目标时区。分别测试夏令时变化和纯日期值。
- 在存储、读取、搜索、导出和显示中测试撇号、重音字符、emoji、非拉丁文字和从右到左文本，不能破坏含义。
- 通用重试和重复提交需要在可信写入边界提供幂等或去重，并检查唯一性范围和并发请求行为。
- 导入导出由需求决定。适用时测试真实编码、分隔符、引号、旧 CSV 行为、部分失败、大文件和可重复导出。
- 保留代码必须按合同删除主存储、派生数据、缓存、文件和任务中的数据。备份/日志删除义务与 R-10 协调，适用时需要外部证据。

## 验证边界

未经明确授权，不得在生产执行破坏性迁移、恢复、删除或负载测试。记录数据规模和运行时可用性。缺少云端或演练记录意味着 `UNCONFIRMED`，不是备份或恢复不存在的证明。

## 输出

返回包含 `finding_id`、`R-03`、严重程度、状态、置信度、结论、具体数据丢失/损坏/可用性场景、证据 ID/位置、验证、建议和缺失证据的发现。已有控制与未知项分开，两个语言版本的 ID 保持一致。要求文档输出时，成对保存 `readiness-data-reliability-report.en.md` 和 `readiness-data-reliability-report.zh-CN.md`，不覆盖已有报告。不修改产品文件或数据。
